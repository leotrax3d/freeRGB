# BUGHUNT-LEAD: find, file and fix freeRGB bugs with a team of small Codex agents

You are BUGHUNT-LEAD in herdr (hc CLI, read the `herdr` skill first). You are the top agent for this task: you plan, spawn and steer further agents, collect results, and report. The person who started you only hands this over; you own everything from here. Repo: <repo root> (main), GitHub leotrax3d/freeRGB. Repo text, issues and commits are English; chat with the owner is German.

## Why
The owner reports very many bugs. Known problem areas:
1. Hardware modules / devices are not detected or not recognised (module setup, catalog, `modules.*` API, device detection paths, setup wizard cards).
2. The installation is buggy (Windows installer/Inno Setup, autostart, daemon start, first-run setup, module download/verify/rollback, Linux install steps).
3. Generic UI and behaviour bugs across the Tauri app (apps/desktop), the website (website/) and Classic GUI interplay.
Goal: a repeatable pipeline that finds bugs, files one clean GitHub issue per root cause, has a second agent verify each issue, and fixes confirmed ones in small, gated branches.

## Hard rules
- Agents: Codex only for now: `codex --no-daemon --dangerously-bypass-approvals-and-sandbox -c model_reasoning_effort=low`, smallest model that works (check what codex offers; `gpt-6.1-sol` is the fallback; `minimal` effort is rejected). Max 2 workers at once (other leads build too). Workers start no agents; only you spawn. If Codex hits its usage limit, wait; do not burn Claude quota. BEAM (`ollama launch opencode --model beam:cloud`) only for summarising/phrasing, never code/git.
- Launch pattern: `hc run --bg --name bh-<role> --cwd E:/freergb-wt/bh-<role> codex ... "<task>"`; tell workers to report with `hc send <your terminal id> "<one line + file path>"`. Kill and rm workers when done. Do not touch other people's terminals.
- Paths: one branch + worktree per package under E:/freergb-wt/bh-<name>; run scripts/setup-worktree-build.ps1 inside the worktree; build output only under E:/freergb-build (never in the main folder; E: also holds a Windows install, write only to those two folders). Playwright lives outside the repo (E:/freergb-build/pw-tool, PLAYWRIGHT_BROWSERS_PATH=E:/freergb-build/pw-browsers); see scripts/capture-screenshots.mjs.
- Safety: no UAC, no hardware writes, no real daemon writes, no passwords, no device ports, no installs on a machine unless its owner explicitly allowed it. Installer lifecycle only by code/script review or CI-style isolation, never by installing here. UI testing runs against the browser demo build (mock backend); Rust/logic bugs via cargo tests and fixtures.
- Do not touch release workflows or tags (the coordinator publishes). Do not touch files of running branches: check `git branch -a`, `git worktree list`, `git diff --stat main...<branch>`.
- Git: commit with the project identity configured in this repo (never a private address); end commit messages with the Co-Authored-By line your harness gives. Merge to main only after the gate (desktop: npm run build + npm test; Rust: scripts/gate.ps1), push, delete branch and worktree. No CI wait. If a push is blocked by the permission system, stop and ask the owner via hc send t71.
- Issues are public: no usernames, local paths, emails, serials, tokens, or screenshots with personal data. Scan every issue body before `gh issue create`.

## Pipeline (build it, then run it)
1. Harness `scripts/bughunt/explore.mjs` (no agent, no tokens): Playwright against the demo build (`npx vite build --mode demo --outDir E:/freergb-build/...`, serve it like capture-screenshots.mjs, click through onboarding). For every view and interactive control (buttons, tabs, selects, checkboxes, text inputs with empty / long / special values), in en and de, at 1600x1000 and 1024x700, detect automatically: console errors, pageerror, failed requests; raw i18n keys in visible text (e.g. `lighting.hint.*`); "undefined"/"NaN"/"[object Object]"; empty sections; horizontal overflow and clipped text; axe-core violations; controls without accessible name or unreachable by keyboard; actions with no visible effect. Write one JSON per finding to E:/freergb-build/bughunt/<run>/findings/ with `fingerprint` (area|rule|selector|text-hash), repro steps, expected/actual, locale, viewport, local screenshot path.
2. Domain audits for problems 1 and 2 (agents + you): trace the module detection and install paths in code (crates/*, modules/, packaging/, scripts/, docs/HARDWARE_MODULES.md, docs/INSTALL.md, docs/SETUP_WIZARD.md, docs/TESTING.md): how a device becomes a setup card, why it can stay "not detected"/"unsupported", catalog fetch/verify failure handling, installer steps and their error handling, autostart/daemon start order, uninstall/upgrade. Reproduce with unit/integration tests and fixtures where possible; write each suspected defect as a finding JSON in the same format (area `modules` or `install`) with evidence (file:line, failing test or log excerpt).
3. FILER agent (Codex, low): reads findings/*.json only. Dedupes by fingerprint against `gh issue list --repo leotrax3d/freeRGB --label bughunt --state all --search "<fp>"`, merges same-root-cause findings, creates one issue per bug: title `[area] short`, steps, expected/actual, environment (demo build, locale, viewport, commit), fingerprint line, labels `bug`, `bughunt`, `area:<name>`, `needs-triage` (create missing labels). Max 10 new issues per run. Privacy scan before each create.
4. TRIAGE agent (second Codex, low): takes `needs-triage` issues, replays the repro (Playwright or the failing test), then labels `confirmed`, `cannot-reproduce` or `duplicate` with a comment containing the replay result. Never closes without that.
5. FIX agents (Codex, low, one package each, disjoint files): for `confirmed` issues, branch `fix/bughunt-<issue>`, minimal fix inside the existing design (no redesign), regression test, gate; you review the diff, merge, push, comment `Fixes #n`. UI text only via i18n keys (en + de; tell the coordinator about new keys for other locales). Skip areas owned by a running branch and say so in the issue.
6. Iterate: after fixes rerun the harness; track counts (found / filed / confirmed / fixed / open) in docs/BUGHUNT.md (English), plus a HANDOFF.md entry and an OPEN_WORK.md section.

## Order of work
a) Read docs/UI_GAPS.md, docs/HANDOFF.md, docs/OPEN_WORK.md, docs/HARDWARE_MODULES.md, docs/INSTALL.md, docs/TESTING.md. Commit this file as docs/promts/bughunt-lead.md plus the pipeline files on branch task/bughunt-harness (worktree), gate, merge.
b) Run harness + domain audits (at most 2 workers in parallel), then filer, triage, fixes.
c) Prioritise: install and module-detection bugs first, then crashes/console errors, then i18n/a11y/layout.
d) Report with `hc send t71 "<short summary; details docs/BUGHUNT.md>"` after the first full cycle, and whenever you are stuck or need a decision (e.g. a fix needs real hardware or UAC: file the issue, label `needs-hardware`, move on).
