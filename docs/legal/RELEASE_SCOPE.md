# Proposed release scope and release-SHA checklist

Status: engineering proposal, 2026-11-08. No release decision or legal approval is recorded by this document. Read [OWNER_DECISIONS.md](OWNER_DECISIONS.md), [RELEASE_FIX_PLAN.md](RELEASE_FIX_PLAN.md), [ASSET_LIST.md](ASSET_LIST.md) and [SBOM_LIMITATIONS.md](SBOM_LIMITATIONS.md) together.

## Proposed scope

Recommend a **public beta**, distributing binaries plus matching source, with explicit hardware limits and online features off. Publisher context supplied by the owner: one private natural person, strictly non-commercial. This records the operating context; it does not resolve applicability of legislation, third-party rights or the remaining owner/lawyer decisions. Publisher identity/contact details and target markets still need recording for publication.

Online/community services, telemetry and download counting must be **OFF by default** in every shipped configuration, including fresh installs and upgrades. No automatic community authentication, identity creation, ratings, receipts or counting requests in that mode. Enabling a service later is a separate owner decision with the corresponding privacy work completed. These are release requirements, not assertions that every current code path meets them. Check update/network behavior separately; any automatic network feature must be disabled for this proposed offline default and explicitly documented before an opt-in. The website is a separate network surface: its Google Fonts import and GitHub release fetch require separate review; desktop offline behavior says nothing about website requests.

Publish a platform/backend/channel matrix with the exact OS, provider, device identity, firmware/driver versions, permitted operations, limitations and linked evidence. Unknown or unrecorded hardware remains experimental; discovery, a compatibility list, a mock test or a successful build does not establish operation on a physical device. Do not generalize one channel's result to a board family. Explain channel role assignment, pump restrictions, recovery limitations and conflicts with other controllers. Hardware-dependent acceptance belongs only in the appended release section of [prompt 07](../promts/fancontrol/07-hardware-acceptance.md).

Build and ship only reviewed modules on `packaging/modules/release-allowlist.txt` (currently `razer-chroma`); allowlisting alone does not resolve D2/D3. Source archives must identify included modules and provenance gaps, including modules omitted from binaries. Exclude unresolved assets/modules from the proposed release or resolve their rights and source obligations before publication. Include matching source for shipped components, build instructions, applicable licence texts, notices and required corresponding third-party source/materials; a repository link alone is not a completeness check. Development effects and tool-only assets are not implicitly approved for runtime packaging.

## Release-SHA checklist (no device access)

- [ ] Freeze the full SHA, clean-tree build inputs, recursive submodule/vendor revisions, platform targets, feature flags and lockfiles. Record reproducible commands and CI run links/log hashes. Confirm the release tag resolves to that SHA.
- [ ] List every downloadable installer, archive, standalone binary, module, source archive, prerequisite/runtime bundle, notice bundle and SBOM. Record exact filename, byte size and SHA-256 of final bytes (after signing, where applicable). Verify downloaded copies against that manifest. Record signatures and verification results separately; checksums alone do not authenticate a publisher.
- [ ] Resolve dependency graphs for each actual target and feature set (Rust workspaces, desktop/website npm, NuGet/native/provider dependencies). Generate the release SBOM and notices from those inputs, then reconcile them against the extracted payload, including embedded fonts, icons, effect WASM, drivers and runtimes. Resolve missing licences/provenance or exclude the component; record remaining gaps. The existing multi-ref source SBOM is not the release SBOM.
- [ ] Match NOTICE, THIRD_PARTY_NOTICES, licence texts, asset attributions, source obligations and SBOM component versions/hashes to the same SHA and artefact set. Check installed paths and source archive contents, not just repository presence. Do not mark absent/planned files as delivered.
- [ ] Verify source archives unpack, contain preferred source/build metadata for shipped effects/modules and locally modified dependencies, and identify exact upstream revisions and patches. Rebuild or explain binary/source differences with evidence; catalog publisher labels are not author attribution.
- [ ] Record results for `cargo fmt --all --check`, `cargo clippy --workspace --all-targets --locked -- -D warnings` and `cargo test --workspace --locked` at the candidate SHA. Include module workflow/source jobs, Linux udev fixture, desktop tests/build and website build for shipped surfaces. Record platform, command, exit status, logs and known exclusions. Mock results remain mock results.
- [ ] Verify offline defaults with isolated/mocked transports and network-request recording: fresh config and migrated config, no community/telemetry/counting traffic, no identity or receipt creation while disabled. Inspect packaged configuration and all startup/network paths, including updater policy. Record methods and coverage limits.
- [ ] Extract Windows installers using a non-executing extractor (record tool/version/command) into a scratch directory; do not launch setup, helper scripts, services or prerequisites. List and hash all extracted payload and inspect installer directives/scripts for extra downloads, temporary payload and embedded components. Likewise list/extract Linux packages and archives without running maintainer scripts. Compare against the build manifest, allowlist, SBOM, notices and source set; investigate every extra/missing file. Extraction failure is an open gate, not permission to run an installer here.
- [ ] Review release notes, onboarding, website and support matrix against evidence; state beta limitations and offline defaults. Resolve or explicitly exclude D2/D3 provenance, D5 wording, D6 branding and D4/D8 online concerns with the responsible owner/lawyer. Record decisions without treating this checklist as legal approval.
- [ ] Attach owner-present hardware/installer execution results from prompt 07 for this candidate and exact hashed installer, or remove affected operations/platform claims from scope. Record remaining failures and exclusions before the owner makes the publication decision. Signing, keys and publishing remain owner/coordinator work; this branch does not publish a release.
