# Desktop localization

English is the source language; German is also shipped. This prepares the desktop
for roughly 50 generated locales without shipping placeholder translations. The
language picker uses each language's native name. New catalogs are marked
**Machine-translated** by default. Automatic selection follows browser/system
language preferences; an explicit choice is remembered and applies immediately.

## Catalogs and typed keys

All translations live in `apps/desktop/src/lib/i18n/locales/<bcp47>.json` as flat,
UTF-8 JSON objects. Use canonical BCP 47 filenames, for example `en.json`,
`de.json`, `pt-BR.json`, `zh-Hant.json`. There is no runtime translation dependency.
`en.json` is the typed source of truth for `MessageKey`, plural base keys and
feature namespaces. Feature `messages.ts` files only export typed helpers:

```ts
import { defineMessages, type FeatureKey } from "@/lib/i18n";
export type CoolingKey = FeatureKey<"cooling">;
export const { t, tn } = defineMessages("cooling");
```

Add a key to English and every shipped locale. Import the feature helper and call
`t()` while rendering or when a helper executes, rather than at module load.
Static label tables should retain message keys or use getters. The shell remounts
its tree after a language change. Catalogs load centrally, including keys in lazy
views, so validation does not depend on which feature has been imported.

English is the fallback for missing translations; unknown keys render as the key.
Messages are plain text, never HTML or Markdown. Render them as React text, never
with `dangerouslySetInnerHTML`. Parameters such as `{name}` are interpolated as
text; do not translate, remove, duplicate or rename placeholders. Device names,
user identifiers and service error details remain as supplied.

## Adding a language

1. Generate `locales/<bcp47>.json` from `en.json`, retaining every English key.
   Catalog discovery and the picker are automatic; no locale union or import list
   needs updating. Exact language tags take precedence over base-language matches.
2. Supply the locale's cardinal plural forms using `_zero`, `_one`, `_two`, `_few`,
   `_many`, `_other` as applicable. `Intl.PluralRules(locale)` selects the category,
   including fractional counts. Every plural family must include every category
   reported by `resolvedOptions().pluralCategories`, plus the English keys for
   source parity. Languages such as Japanese may retain unused `_one` entries.
   Arabic requires all six forms. `tn("feature.items", count)` fills `{count}`.
   Missing forms fall back to `_other`, then the English category for that count.
3. Run validation for that language, then the full desktop checks:

   ```sh
   node scripts/validate-i18n.mjs ar
   node scripts/validate-i18n.mjs all
   cd apps/desktop
   npm run i18n:validate -- de
   npm test
   npm run typecheck
   npm run build
   ```

The validator checks keys, nonempty strings, exact placeholder multisets, malformed
placeholders, HTML/entities/Markdown markup, BCP 47 tags and locale-specific plural
completeness. It accepts one locale or `all` (the default), reports errors with the
locale and key, and exits nonzero. `npm test` runs it before Vitest. Node must have
ICU support for the target locales (the supported project Node distribution does).

## Translation provenance and fan safety

`src/lib/i18n/locale-metadata.json` holds explicit `machineTranslated` and `reviewed`
flags. Missing entries default to machine-translated and unreviewed. English is
reviewed; German includes machine-translated additions and its safety wording is unreviewed.
Only set `reviewed: true` after a qualified reviewer checks the complete catalog,
including pump, unrestricted unlock, fail-safe and channel-test warnings. Updating
safety wording in English or regenerating a translation requires clearing the
locale's reviewed flag until it has been checked again.

Unreviewed locales also show the interpolated English text for safety messages.
The policy in `isSafetyMessage()` conservatively includes longer cooling,
onboarding and setup explanations, shorter messages with safety-related terms,
the pump minimum warning, and cooling validation errors. Compact control/status
labels stay concise. When adding a short safety warning, check that this policy
recognizes its key. Missing translations already display English and are not
repeated. English plural safety text uses English plural rules independently.

The versioned fan-control notice in `features/onboarding/safety.ts` remains the
original English acknowledgement. Its wording and `SAFETY_TEXT_VERSION` must stay
in sync with the daemon; this task does not change that contract.

## Direction, fonts and expanded text

The document's `lang` and `dir` follow the selected locale. Arabic, Hebrew, Persian
and Urdu (including regional variants) use RTL. Layout spacing/alignment uses
logical Tailwind utilities (`ms`, `me`, `ps`, `pe`, `start`, `end`, `text-start`).
Radix selects and sliders receive the direction explicitly for keyboard behavior.
Physical coordinates in device canvases, color fields and charts retain their
meaning; do not mirror their underlying geometry.

The font stack includes local CJK, Thai and Indic fallbacks, including Noto and
Windows script fonts, then system fonts. These are local fallbacks, not network
font downloads. Hosts need fonts for the scripts they display. Buttons and select
items grow vertically and wrap; form fields stay within their containers. Avoid
new fixed text widths/heights and unnecessary `whitespace-nowrap`.

Development builds expose **Pseudo (expanded)** (`en-XA`) in the picker. It accents
and brackets all English messages and expands them by about 40%, retaining
placeholders. Check every view at narrow widths: unbracketed prose reveals
hardcoded text, and clipping reveals layout constraints. The pseudo-locale is not
included in production builds.

Vitest checks pseudo expansion, placeholders and rendered controls. The UI source
scan rejects raw JSX prose and literal accessible labels; its explicit allowlist
contains technical tokens, command examples and branding. Keep that list limited
to text that must stay identical in all locales. The scan does not replace manual
pseudo-locale review of conditional strings, service-provided data or layout.

## Accessibility

Retain labelled controls, landmarks, the skip link, focus restoration and keyboard
navigation. Errors use alert semantics, status updates use status semantics, and
information must not depend solely on color. Native language names carry their
own language tag in the picker. English safety text stays visible alongside the
translation; neither hardware actions nor elevated prompts are required for
localization tests, which render simulated state only.
