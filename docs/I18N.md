# Desktop app: languages (i18n) and accessibility

The desktop app (`apps/desktop`) is available in **English** (source language) and **German**.
The language follows the system language by default and can be changed under
**Settings → Language**; the choice applies immediately and is remembered in the browser/webview storage.

## How it works

* `src/lib/i18n/index.ts` is a small framework without runtime dependencies:
  `t(key, params)`, `tn(key, count, params)` for plurals, `defineMessages(prefix, { en, de })` for
  feature catalogs, and the `useLocale` store.
* The core catalog (navigation, shell, shared components, tour, palette) lives in
  `src/lib/i18n/en.ts` and `de.ts`. `de` is typed as `Record<keyof typeof en, string>`, so a missing
  German key is a compile error.
* Every other feature owns a `messages.ts` next to its view (`features/<name>/messages.ts`) that calls
  `defineMessages("<prefix>", { en, de })`. Keys must start with the prefix (checked at start-up).
* English is the fallback for any missing key; an unknown key renders as the key itself.
* Switching the language remounts the app tree (the shell is keyed by locale), so plain `t()` calls in
  render code, memoised components and helpers pick up the new language without extra subscriptions.
  Because of that, call `t()` at render time, never at module load (except as default parameter values
  evaluated per call).
* Placeholders are `{name}`; plural pairs use the suffixes `_one` / `_other`, and `{count}` is filled in.
* Static tables that hold labels (navigation, effect fields, phases, blend modes) store **message keys**
  and are translated where they are rendered.

## Adding strings to a feature (cooling, macros, any new view)

1. Create `features/<name>/messages.ts`:

   ```ts
   import { defineMessages } from "@/lib/i18n";

   const en = { "cooling.title": "Cooling" } as const;
   const de: Record<keyof typeof en, string> = { "cooling.title": "Kühlung" };

   export type CoolingKey = keyof typeof en;
   export const { t, tn } = defineMessages("cooling", { en, de });
   ```

2. Import `t` from that file in the components and replace every user-visible string, including
   `aria-label`, `title`, placeholders, toasts and error messages thrown for the user.
3. Import the new `messages.ts` in `src/lib/i18n/i18n.test.ts` so the parity test (same keys and same
   placeholders in both languages) covers it.

`features/cooling/` and `features/macros/` are not translated yet; they appear in English until they adopt
this pattern. Raw text from the service (device names, error details from the daemon, sensor names) is
shown as delivered.

## Intentionally English

* The fan-control **safety notice** (`features/onboarding/safety.ts`). Its text is versioned and the
  acknowledgement refers to the exact wording; a German version needs a reviewed legal translation and a
  new `SAFETY_TEXT_VERSION`. The wizard says so next to the notice.
* Product and technical names (freeRGB, Classic, `--no-state`, file names).

## Accessibility conventions

* Keyboard: skip link to the main content, focus moves to the main area after a view change, arrow keys
  move through the sidebar, modal dialogs (command palette, tour) trap focus and restore it on close
  (`useFocusTrap` in `src/lib/a11y.ts`), the region canvas is operable with arrow keys (Alt resizes).
* Screen readers: landmarks (`nav`, `main` with the view name), grouped navigation, labelled sliders and
  colour controls (`aria-valuetext` on the colour area), icons are `aria-hidden`, errors use
  `InlineError`/`ErrorState` (`role="alert"`, icon plus text, never colour alone), status messages use
  `role="status"`.
* The document language (`<html lang>`) follows the selected language.

## Tests

`npm test` in `apps/desktop` covers locale detection, interpolation, plurals, fallback, key parity and
placeholder parity between English and German, and the focus-wrap helper.
